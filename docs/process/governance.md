# Governance

Status: Accepted

Decided in [ADR-0027](../decisions/ADR-0027-governance-and-repository-settings.md).

## Roles

| Role | Responsibilities |
|---|---|
| **Repository owner** | GitHub administration: settings, secrets, packages, environments; an offline backup of signing secrets |
| **Lead maintainer** | Technical direction; accepts ADRs; reviews and merges; approves releases through the `release` environment; generates signing keys |
| **Contributors** | Changes through pull requests following the [workflow](workflow.md) |

The primary contributors are listed in [ADR-0026](../decisions/ADR-0026-branding-and-identifiers.md) and the README.

## Decision making

- Technical decisions are proposed as ADRs and accepted by the lead maintainer.
- Changes visible outside the repository (tags, releases, settings, packages, publishing) are made by maintainers, or requested from the repository owner, never by automation without approval.

## Repository settings checklist

Applied by the repository owner:

- [x] Visibility: public.
- [x] Default branch: `v1` during the rebuild, so features that read only the default branch (issue templates, `SECURITY.md`, CodeQL default setup, Dependabot, release-please) work. `main` becomes the default again at the [switch-over](workflow.md#switch-over) ([ADR-0030](../decisions/ADR-0030-rebuild-on-a-v1-branch.md)).
- [x] Protection on both `main` and `v1`, as rulesets with an empty bypass list (required status checks follow CI's first run):
  - require pull requests
  - require status checks (the CI gates in [workflow](workflow.md#ci-gates-required-to-merge)); on `v1` they are added after CI's first run ([RB-01](../runbooks/m1-foundation.md#rb-01-toolchains-and-safety-net)), because a check can only be required once it has run
  - require linear history
  - block force pushes and deletion
  - no required approvals
- [x] Pull requests:
  - squash merging only, with the **title set to the PR title and the message left blank** ([workflow](workflow.md#branches-and-commits))
  - automatically delete head branches
- [x] `CODEOWNERS` assigns the lead maintainer.
- [x] Actions:
  - default `GITHUB_TOKEN` permissions read-only
  - allow GitHub-authored actions and the [allowlist](#allowed-actions) of third-party actions only
  - require actions to be pinned to a full-length commit SHA
  - fork pull requests get no secrets
  - allow Actions to create pull requests (for release-please)
- [x] Environment `release` with the lead maintainer as required reviewer.
- [ ] Secrets: `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, generated by the lead maintainer, with an offline backup kept by the repository owner. Later: the code signing credentials, the PyPI trusted publisher, and the release App's id and private key (see [key custody](#key-custody)).
- [ ] Packages: GHCR image `folo` public, linked to the repository.
- [x] Security: Dependabot alerts and security updates, secret scanning and push protection, CodeQL default setup, private vulnerability reporting (the channel [`SECURITY.md`](../../SECURITY.md) points to).
- [ ] Releases: release-please allowed to open PRs, using a GitHub App installation token ([ADR-0019](../decisions/ADR-0019-ci-cd-versioning-and-releases.md)).

## Allowed actions

Workflows use GitHub-authored actions (`actions/*`, `github/*`) and the third-party actions listed here, each pinned to a full commit SHA. Dependabot keeps the pins current. To add an action, open a pull request that adds it to this list and says why it's needed. A run book that introduces an action adds it here in the same pull request.

| Action | Used for |
|---|---|
| `googleapis/release-please-action` | The release PR and changelog ([RB-23](../runbooks/m8-release.md#rb-23-release-pipeline)) |

CodeQL runs from GitHub's default setup only. A CodeQL job in a workflow conflicts with it, so no workflow adds one.

## Key custody

| Key | Holder | Rotation |
|---|---|---|
| Update signing key | GitHub secret; offline backup with the repository owner | A rotation ships a release signed by the old key that adds the new public key, then switches |
| Release App private key | GitHub secret (with the app id); the App is created and owned by the repository owner | Generate a new key in the App's settings, update the secret, delete the old key |
| Node identity keys | Each node, in its `secrets.json` | `folo pair reset` (re-pairing required) |
| Client keys | Hashed on the controller | Revoke per client; master key with `folo token rotate` |
| Device credentials (Hue app keys and client keys, WLED PINs, Hyperion tokens) | The controller's `secrets.json` | Re-pair or re-enter |
