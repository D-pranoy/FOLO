# ADR-0020: OTA updates

Status: Accepted
Date: 2026-10-13

## Context

Nodes should update from GitHub Releases, with approval. Sources are managed centrally by their controller. Tauri's updater supports only some install types and doesn't fit services or approvals.

## Decision

- **D1.** **One updater, inside the node**, for every install type.
  - It applies updates itself for: Windows installer (desktop or service), portable and headless archives (A/B folders), AppImage.
  - It notifies only for: deb, rpm, AUR, Docker.
- **D2.** Artifacts are signed with the **update signing key** in Tauri's minisign-compatible format and verified with `minisign-verify` against a public key built into FOLO. Verification can't be turned off.
- **D3.** **Approval policy** lives on the controller: manual per node (default), automatic for patch releases, or maintenance windows. Sources report available updates to their owner controller.
- **D4.** **Channels:** stable and beta.
- **D5.** **Order and compatibility:** the controller updates first when the protocol version changes. Sources of the same major version and up to one minor version older are supported.
- **D6.** **Health check** within 120 s of restarting. Archive installs roll back automatically; installer installs notify.
- **D7.** The update signing key is generated by the lead maintainer, stored as a GitHub Actions secret, and backed up offline by the repository owner ([ADR-0027](ADR-0027-governance-and-repository-settings.md)).

## Alternatives considered

| Option | Pros | Cons |
|---|---|---|
| Tauri updater for desktops plus a second updater for headless nodes | Reuses Tauri | Two updaters; no service or approval support |
| Notify only | Trivial | Doesn't meet the requirement |
| Staged percentage rollouts | Limits blast radius | Approvals already gate updates; a later option |

## Consequences

Packaging writes an install-type marker. Details: [updates](../architecture/updates.md).
